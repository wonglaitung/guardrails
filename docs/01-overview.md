# 01 - 项目概述与架构总览

## 项目背景

### 问题陈述

在使用大语言模型（LLM）的应用中，存在两类主要风险：

1. **PII 泄露风险**: 用户可能无意中在提示词中包含身份证号、手机号、银行卡号等敏感信息
2. **语义攻击风险**: 恶意用户可能使用隐晦的提示词注入、越狱攻击等手段绕过安全限制

传统单层防护方案存在明显局限：
- **纯规则检测**: 无法识别语义层面的攻击
- **纯 LLM 检测**: 延迟高、成本高，不适合格式化 PII

### 解决方案

构建**双层护栏系统**：

## 核心概念

### Layer 1: PII 规则检测层

基于 Microsoft Presidio 和自定义正则表达式的精准检测：

```python
class ChinesePIIGuardrail:
    """Layer 1: PII 检测与脱敏"""
    
    def detect(self, text: str) -> List[PIIEntity]:
        """检测文本中的 PII 实体"""
        
    def redact(self, text: str) -> str:
        """脱敏处理，替换为占位符"""
```

**支持的 PII 类型**：

| Entity Type | 描述 | 示例 |
|-------------|------|------|
| CN_PHONE_NUMBER | 中国手机号 | 13812345678 |
| CN_ID_CARD | 身份证号 | 110101199001011234 |
| CN_BANK_CARD | 银行卡号 | 6222021234567890 |
| CN_PASSPORT | 护照号 | E12345678 |
| CN_SOCIAL_CREDIT_CODE | 统一社会信用代码 | 91110108MA01234567 |
| CN_LICENSE_PLATE | 车牌号 | 京A12345 |
| HK_PHONE_NUMBER | 香港电话 | 51234567 |
| HK_ID_CARD | 香港身份证 | A123456(7) |
| EMAIL_ADDRESS | 邮箱 | test@example.com |
| IP_ADDRESS | IP地址 | 192.168.1.1 |

### Layer 2: LLM Judge 层（可选）

基于 Qwen3Guard-8B-Stream 的语义风险检测：

```python
class ComplianceJudge:
    """Layer 2: 内容安全裁判"""
    
    async def judge(self, content: str, context: str = None) -> JudgeResult:
        """判断内容是否安全"""
        
    async def quick_check(self, content: str) -> float:
        """快速安全分数检测（用于流式拦截）"""
```

**风险等级**：

| 等级 | 说明 | 处理方式 |
|------|------|----------|
| SAFE | 安全内容 | 正常放行 |
| LOW | 低风险 | 记录日志，放行 |
| MEDIUM | 中风险 | 记录日志，可选拦截 |
| HIGH | 高风险 | 拦截请求 |
| CRITICAL | 严重风险 | 拒绝请求，通知管理员 |

### 代理转发

支持 OpenAI 和 Claude API 格式的透明代理：

```
客户端 → Gateway → 上游服务
         ↓
      PII/Judge 检测
```

**支持的 API 端点**：

| 端点 | 格式 | 说明 |
|------|------|------|
| `/v1/chat/completions` | OpenAI | 聊天完成 |
| `/v1/completions` | OpenAI | 文本完成（旧版） |
| `/v1/messages` | Claude | Claude 3 消息 |
| `/v1/models` | OpenAI | 模型列表 |
| `/health` | - | 健康检查 |

## 设计决策记录 (ADR)

### ADR-001: 为什么选择双层架构？

**决策**: 采用 Layer 1 (规则) + Layer 2 (LLM) 的双层架构。

**原因**:
1. **互补性**: 规则检测精准快速，LLM 检测语义理解强
2. **性能**: Layer 1 可在 <1ms 内完成，Layer 2 可选启用
3. **成本**: 大部分请求只经过 Layer 1，减少 LLM 调用成本
4. **准确性**: 格式化 PII 用规则，语义攻击用 LLM

**权衡**:
- 增加了系统复杂度
- 需要维护两套检测逻辑

### ADR-002: 为什么基于 Microsoft Presidio？

**决策**: Layer 1 基于 Microsoft Presidio 构建。

**原因**:
1. **成熟稳定**: 微软开源项目，经过大量生产验证
2. **可扩展**: 支持自定义 Recognizer，便于添加中国特有 PII
3. **多语言**: 内置多语言支持，我们扩展了中文字体检测

**权衡**:
- 依赖 spaCy 模型，需要额外下载
- 默认对中文支持有限，需要自定义识别器

### ADR-003: 为什么选择 Qwen3Guard 作为 Judge？

**决策**: Layer 2 使用 Qwen3Guard-8B-Stream 模型。

**原因**:
1. **流式优化**: 专为流式场景设计，支持增量输出
2. **中文优化**: 对中文内容理解更准确
3. **轻量级**: 8B 参数量，可部署在消费级 GPU
4. **快速响应**: 无 CoT 模式可在 <500ms 返回结果

### ADR-004: 为什么作为代理而非 SDK？

**决策**: 设计为 HTTP 代理服务，而非纯 SDK 库。

**原因**:
1. **透明集成**: 客户端无需修改代码，只需修改 API endpoint
2. **统一管理**: 所有请求经过统一入口，便于监控和审计
3. **语言无关**: 任何语言的应用都可以使用
4. **部署灵活**: 可独立部署、水平扩展

**权衡**:
- 增加了网络延迟（约 1-5ms）
- 需要额外的运维工作
